# Wayland screen context: implementation and acceptance

Refs [issue #26](https://github.com/ralphschuler/orbitpal/issues/26). The ScreenCast/PipeWire backend and local lifecycle fixtures are implemented. **The real GNOME and KDE capture acceptance criteria remain open.** A macOS fixture run does not validate a Wayland desktop.

## Runtime and build requirements

Linux needs the session D-Bus, PipeWire, xdg-desktop-portal and its desktop-specific ScreenCast backend. The compositor controls which monitors can be selected. Build hosts additionally need `libpipewire-0.3-dev` and `libclang-dev`; CI and Linux release builds install these alongside the existing Tauri prerequisites. No capture helper process, screenshot file, global PipeWire socket, XWayland fallback or external model service is used.

The Studio's explicit selection opens one monitor with `persist_mode=0` where supported. Restore tokens are neither requested for reuse nor stored. A private D-Bus connection owns the session and observes `Session::Closed` and connection loss. The PipeWire connection is created exclusively from `OpenPipeWireRemote`'s restricted FD. Registry/listener/core/FD handles are owned by its bounded-poll worker. Between requests the worker observes source removal but has no video stream or pixel cache.

Clicking the source-selection button first saves this bot's current settings, including the visible model configuration, then opens the chooser. A changed bot/draft or disposal during preparation prevents selection. A successful chooser result that becomes stale is disconnected by its exact lease ID; cleanup cannot disconnect a newer selection or another bot. Cleanup errors remain visible through the app notification even if the panel was closed. A pending chooser is still bounded by the native selection timeout; this does not claim immediate OS-dialog cancellation when leaving the panel. Save again after choosing a source to commit its new display ID.

Portal v6's `pipewire-serial` targets `PW_KEY_TARGET_OBJECT` (`target.object`). A v6 response without a valid serial is rejected. Older portals resolve the selected node's `object.serial` once from the restricted registry during explicit connection. All later streams use that fixed serial and `DONT_RECONNECT`. Source destruction closes the session; a recycled numeric node ID cannot silently select a different monitor. [ScreenCast specification](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html).

Every inference request creates a new video stream, samples a newly delivered CPU frame and destroys the stream. Selection alone produces no frame. Only mapped MemPtr/MemFd RGBx/RGBA/BGRx/BGRA buffers are accepted; encoded/GPU-only formats are rejected explicitly. Dimensions, stride, chunk extent and corruption are checked before copying. The existing 64-megapixel/16,384-edge source budget, 1,280-edge JPEG output and image/message budgets remain in force. A bounded five-second frame wait and cooperative cancellation release per-request streams. [PipeWire stream API](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/stream/struct.Stream.html).

Session ownership is per bot. The host's persisted screen/image grants and model destination still authorize each request. Session closure also cancels attached turns so late images/model output cannot commit; profile revision checks remain active around capture and inference. Changing a different bot does not transfer its session. Global Stop, explicit disconnect and app exit close sessions. OS process teardown also closes the private D-Bus connection; no permission restore token survives.

## Evidence and remaining manual matrix

Local fixtures use synthetic colored images and in-memory queues. They cover separate lease/grant identity, bot/model/display binding, replacement, revocation, Stop, distinct per-request results and discarding a frame delivered after revocation. A two-bot fixture checks that switching Studio context cancels only its old tickets, retains both explicitly selected leases, prevents cross-bot source reuse and leaves the other bot intact on disconnect. Existing screen-context fixtures additionally cover off/on revisions, image budgets and fresh provider messages. These fixtures do not connect to a real portal or PipeWire desktop.

| Environment | Compilation / fixture evidence | Real screen capture acceptance |
| --- | --- | --- |
| macOS host | Portable session code compiled and initial lifecycle fixtures passed; no Wayland backend compiled on this host | Not applicable; no real screens captured |
| Linux ordinary CI | Native backend compile and fixture run required on this PR's exact final head | Fixtures alone cannot establish compositor acceptance; the separate disposable-desktop job exercises its explicitly listed real cases |
| Current GNOME Wayland | Pending a real session with its installed portal backend | **Pending** |
| Current KDE Plasma Wayland | Pending a real session with its installed portal backend | **Pending** |

For each real desktop, record distro, desktop/compositor, portal/PipeWire versions, app commit and pass/fail for the following operator checks. Use a synthetic desktop containing no private content and a local image-capable model or transport fixture; do not publish screenshots in the issue.

1. Enable screen/image permissions for one bot, select exactly one monitor in the compositor dialog, save, then request two distinct synthetic desktop states. Verify the receiving fixture gets the corresponding new JPEG each time, with no image in history, Hindsight, profile export or temporary screenshot files.
2. Cancel the system dialog, deny access, stop the portal service and disconnect/revoke through the compositor. Each action must close/cancel the affected turn and show a truthful reconnect state. Reopening the settings or restarting OrbitPal must not restore a lease automatically.
3. While capture or model delivery is pending, disable capture, change its monitor or model destination, switch bots, press global Stop and quit. No late result may be committed or replayed. A newly selected session must not revive an old turn. Confirm a second bot cannot use the first bot's source ID. A Studio bot switch cancels the old request tickets while retaining each bot's independent, explicitly selected lease; configure two bots and verify each can make a fresh request using only its own source. Disconnecting one bot must leave the other's lease and requests intact.
4. Remove/reconfigure the selected monitor, suspend/resume and reconnect devices. Verify source removal closes the lease and a reused numeric PipeWire node cannot retarget it. Exercise portal v6 serial targeting where available and the legacy serial-discovery path on an older portal.
5. Exercise scaled/rotated and multiple monitors, static and changing desktops, wide resolutions, CPU-format negotiation and a backend that offers only unsupported buffers. Confirm bounded JPEGs or explicit errors, with no fallback monitor or stale cached frame.
6. After Stop/disconnect/quit, confirm the compositor sharing indicator disappears and PipeWire streams/FDs are released. While merely connected but idle, confirm no OrbitPal video-receive stream exists. Repeat selection/cancellation to check that resources do not accumulate.

Keep issue #26 open until both desktop rows and the applicable lifecycle cases have actual evidence. Do not replace pending rows with inferred success from compile logs or fixtures.


## Experimental desktop evidence

A separate acceptance prototype in [PR #56](https://github.com/ralphschuler/orbitpal/pull/56) captured two fresh synthetic images through the real GNOME 46 portal. The historical packaged KWin 5.27 virtual backend granted sharing and negotiated a running PipeWire stream but produced no frames. That observation is a failed KDE result, not proof that longer consumer timeouts would fix it. The cited [KWin texture/change fix](https://github.com/KDE/kwin/commit/309c9100fa6b1ce0f17e0f927091ff851dd5c06d) dates to 2023; it is not a newly released fix.

The updated, still opt-in workflow targets disposable **Ubuntu 26.04** jobs for both packaged current desktops. A [read-only runner probe](https://github.com/ralphschuler/orbitpal/actions/runs/39407190932) established kernel 7.0, available `vgem`/`vkms` modules and an existing Hyper-V DRM node. It did not load a module, open a chooser or capture a frame. The subsequent acceptance attempt must pass every real assertion; capability evidence alone is insufficient.

The harness creates a fresh nonroot account, private home/runtime/config and private D-Bus/PipeWire services. It loads only a previously absent `vgem` software module, identifies exactly its genuine primary node through sysfs, and gives only the isolated account read/write access to that new node. Existing Hyper-V/physical devices and their permissions stay untouched. Cleanup kills that account's processes, removes its private files/account and unloads only the module it loaded. The entry points refuse ordinary developer/self-hosted sessions. No host desktop, personal account, credentials or OS privacy grants are reused.

The first Ubuntu 26.04 attempt failed before any chooser/native capture assertion. GNOME stopped at the strict private-device check, with insufficient metadata to distinguish open/owner/mode failure. KDE passed genuine GBM/EGL and OpenGL compositor checks, but KWin had auto-activated a frontend before the private display/configuration was published; that stale daemon exposed no ScreenCast interface. The harness waits for real udev initialization before granting its exact new node and records bounded owner/mode/error diagnostics. It starts the actual frontend with the documented `--replace` option only on its private bus, and requires both backend and frontend names to belong to the exact spawned PIDs.

The [second actual attempt](https://github.com/ralphschuler/orbitpal/actions/runs/39411523830) at PR merge `2aef05a` (branch `60a335d` plus base `d4e13cd`) passed the complete current GNOME prototype: real chooser allow/cancel/reselect, two fresh red/blue JPEGs, bot/model isolation and close invalidation. KDE 6.6.6 passed the real rendering/compositor and daemon-owner gates, then its backend rejected `CreateSession` because `zkde_screencast_unstable_v1` was unavailable. No KDE chooser/frame/cancel assertion passed. Bounded artifacts also showed that `kbuildsycoca6` could not find `applications.menu`.

The isolated KDE startup supplies `XDG_MENU_PREFIX=plasma-` before cache/KWin startup, requires the packaged `plasma-applications.menu`, and publishes only that variable to its private activation bus. This follows [Plasma 6.6.6 startup](https://github.com/KDE/plasma-workspace/blob/v6.6.6/startkde/startplasma.cpp) and preserves the packaged portal's [restricted-interface declaration](https://github.com/KDE/xdg-desktop-portal-kde/blob/v6.6.6/data/org.freedesktop.impl.portal.desktop.kde.desktop.in). The inference was that the missing menu/cache prevented [KWin's normal executable authorization](https://github.com/KDE/kwin/blob/v6.6.6/src/wayland_server.cpp) from finding that declaration. The [third actual attempt](https://github.com/ralphschuler/orbitpal/actions/runs/39414253734), at PR merge `ad3d879` (branch `9d680e9` plus base `b83e402`), observed KWin's exact authorization of the canonical packaged backend and screencast interface, then passed the complete KDE prototype. Only the specific `kwin_core`/`KWIN_UTILS` debug categories are enabled on this private compositor, through the existing bounded text collector. Permission filters stay enabled.

That third attempt failed on GNOME before the chooser or capture test: an auto-activated backend owned its bus name instead of the explicitly spawned backend. The strict owner gate correctly refused it. The harness now starts the real GNOME 50.0 backend with its supported [`--replace` option](https://gitlab.gnome.org/GNOME/xdg-desktop-portal-gnome/-/blob/50.0/src/xdg-desktop-portal-gnome.c), only after verifying the private session bus. The exact spawned-PID requirement remains unchanged; failure diagnostics contain bounded numeric owner metadata. KDE arguments and production capture behavior are unchanged. GNOME and KDE have each passed on separate reviewed heads; both must pass together at the next head before claiming a current baseline matrix. The full application acceptance matrix remains open.

The [fourth attempt](https://github.com/ralphschuler/orbitpal/actions/runs/39416613629), at PR merge `d0065d8` (branch `9ed1429` plus base `b0c1288`), passed GNOME's complete baseline. KDE passed the initial chooser and both fresh red/blue production captures, then its Cancel input gate failed: AT-SPI exposed the second chooser while fresh KWin metadata still contained zero matching windows. The controller correctly sent no Escape; the later native selection deadline expired. This supports a compositor mapping/focus race rather than a frame failure. The controller now waits within its existing 25-second action deadline for a fresh exact-PID mapped and active chooser. It records an attempted cancellation only after genuine Escape dispatch. Stale, malformed, foreign or ambiguous metadata still fails, and observed dismissal plus native cancellation remain required. No timeout, production capture behavior or input authorization gate was relaxed. Both desktop baselines still need a common-head pass.

Before opening a chooser, a native capability probe must allocate a real exportable GBM buffer and render/read a small synthetic texture through its actual GBM/EGL context. It supplies no portal response, source texture or PipeWire buffer. KDE must additionally report an active OpenGL compositor; QPainter is an explicit failure. These checks follow [KWin 6.6.4's vgem/virtual backend](https://github.com/KDE/kwin/blob/v6.6.4/src/backends/virtual/virtual_backend.cpp), [GBM/EGL setup](https://github.com/KDE/kwin/blob/v6.6.4/src/backends/virtual/virtual_egl_backend.cpp) and [OpenGL output screencast implementation](https://github.com/KDE/kwin/blob/v6.6.4/src/plugins/screencast/outputscreencastsource.cpp). Qt6, `kbuildsycoca6` and the actual packaged desktop versions are recorded. The private synthetic monitor is 1,280 × 960; the production 1,280-edge JPEG budget and five-second fresh-frame wait remain unchanged.

GNOME uses the real [Share Screen dialog](https://github.com/GNOME/xdg-desktop-portal-gnome/blob/50.0/src/screencastdialog.ui). In [KDE 6's single-choice chooser](https://github.com/KDE/xdg-desktop-portal-kde/blob/v6.6.4/src/PipeWireLayout.qml), clicking a monitor card itself accepts sharing; there is no separate Share button. The controller binds that card to the exact output name read from the private compositor, excludes region/new-virtual resources, and observes real dialog dismissal. Cancel uses a genuine Escape event only after fresh metadata confirms the exact chooser process has keyboard focus. KWin's normal executable/interface authorization remains enabled. Input is restricted to this generated compositor and registered helper, never a normal user desktop. Neither an accepted accessibility action nor delivered input alone counts as portal consent: the native test independently requires the real success/cancel response and fresh captured colors.

Successful baseline receipt requires genuine chooser allow/cancel/reselect, distinct fresh red/blue JPEGs, cross-bot rejection, model-change cancellation and close invalidation. Only bounded text diagnostics are uploaded; captured frames remain in memory. No skipped, failed or capability-only job counts as successful capture. The full actual Studio/provider/history, two-bot, revocation, display/lifecycle and resource matrix above remains open in #26 even after this baseline succeeds.
