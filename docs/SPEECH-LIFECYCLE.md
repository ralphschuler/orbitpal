# Speech presentation and cancellation

An assistant reply is an in-memory speech job until playback actually starts. The same rule applies to a deliberate voice-disabled presentation. The first valid start acknowledgement writes the assistant message to its originating bot's local history with the speech job ID. Repeated acknowledgements do not create duplicates. A pending reply does not enter the next model request or survive an app restart. Stop and synthesis failures leave the user's question in history without inventing an unheard answer. Stopping after playback has started keeps the already presented answer.

Each job captures its voice provider, language, system voice selection, rate, pitch, volume and enabled state. Studio, the native character window and OBS use this public snapshot. Cloud credentials, credential references, model names and private endpoints are not included in renderer events. Editing a voice affects subsequent jobs.

The Studio assigns an immutable UUID before asynchronous setup or IPC. Native code validates it and rejects active/recent reuse and IDs already in persisted history; callers that omit it receive a native UUID. Start, completion and cancellation events can therefore be matched even before the request RPC returns. Old callbacks cannot borrow another turn's ID. Recent IDs expire after four minutes and are capped at 4,096; native watchdogs additionally bind their exact cancellation token, so a delayed timer cannot cancel a replacement with a reused ID. Cancelling an autonomous playback releases its scheduler lease before invalidating the UI turn.

Native-window and OBS jobs have a 180-second completion watchdog, matching the Studio's acknowledgement wait. On expiry, the host invalidates only that bot/job pair, removes its audio and notifies renderers to stop that exact utterance. A late acknowledgement or synthesis result cannot revive the job. The Studio can also request this exact cancellation from its timeout handler; this command is restricted to the main window. A timer for an already completed or stopped job does nothing. Studio playback retains the player's own completion/error lifecycle.

The native encoded-audio cache has a 64 MiB logical-byte budget, including encoded audio, MIME strings and cache keys. It evicts least recently requested entries that are not currently playing. Playing jobs are pinned for safe retries; a new request fails explicitly if the remaining budget cannot fit it. Individual encoded payloads remain limited to the base64 equivalent of 25 MiB of source audio. This is a cache budget, not a claim about total process memory: response copies, decoding and renderer buffers have their own lifetimes. Completion, cancellation and per-bot Stop immediately remove the corresponding cached data. Cache invalidation never waits for a provider request to finish.

Regression checks use temporary stores, in-memory audio and fake timers. They do not record microphones, synthesize paid speech or post to streams. Live OBS/audio-device behavior is not covered by these fixtures.
