# Releases

Pull requests and changes on `main` run the CI workflow on Linux, Windows, and macOS. Each platform runs `pnpm check`, `pnpm test:run`, the frontend build, packaging-script tests, and `cargo test --locked`. Tests use local fixtures and HTTP mocks; they do not need live model, voice, streaming, or Hindsight accounts.

## Publish a version

1. Update the version in `package.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`. Update `Cargo.lock` by running Cargo normally, then verify it with `node scripts/release-info.mjs`.
2. Complete the checks and merge the release commit.
3. Create and push its matching tag, for example `v0.4.0`. The existing tag can also be selected through the manual release workflow.
4. The workflow checks all version files, reruns CI for the tagged commit, then builds all four targets. Only when every build succeeds does its final job receive permission to create a release.

Tags must match the version exactly. A prerelease suffix such as `v0.4.1-rc.1` creates a GitHub prerelease. Existing releases are never overwritten automatically. If a publication failed after creating its draft, inspect that draft before removing it or creating a new version.

## Downloads

| Target | Downloads |
| --- | --- |
| Windows x64 | NSIS `.exe` installer and MSI |
| macOS Apple Silicon | `.app` ZIP and DMG |
| macOS Intel | `.app` ZIP and DMG |
| Ubuntu 24.04 x64 | AppImage and Debian package |

All names contain the version and architecture. The release also includes a source ZIP and `SHA256SUMS`. On Linux run `sha256sum --check SHA256SUMS`; on macOS run `shasum -a 256 --check SHA256SUMS` after downloading the listed assets.

Before packaging, `scripts/third-party-notices.mjs` collects installed JavaScript and locked Rust dependency notices into `public/licenses/DEPENDENCIES.txt`, which is bundled with the app. Releases also attach JSON inventories generated by `pnpm licenses list --json` and `cargo metadata --format-version 1 --locked`; those inventories describe dependencies and do not replace their license texts.

The initial pipeline has no signing secrets. Windows downloads are unsigned; macOS bundles are ad-hoc signed and not Apple-notarized. These limitations are included in every release's notes. Do not describe them as signed or notarized developer releases. A future signing setup should keep credentials in trusted release environments, never in pull-request workflows or the repository.

## Workflow boundaries

Release workflows run only for pushed version tags or explicit manual dispatch. They do not run from `pull_request_target` or from untrusted pull-request artifacts. CI and build jobs have read-only repository permissions; only the final publication job has `contents: write`. Checkout tokens are not persisted, third-party actions are pinned to verified commit hashes, and no model or service credentials are provided.
