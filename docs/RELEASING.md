# Releases

Pull requests and changes on `main` run the CI workflow on Linux, Windows, and macOS. Each platform runs `pnpm check`, `pnpm test:run`, the frontend build, packaging-script tests, and `cargo test --locked`. Tests use local fixtures and HTTP mocks; they do not need live model, voice, streaming, or Hindsight accounts.

Linux CI and the Linux release build also run the focused `glib_variant_regression` test with `--release` optimization. It exercises the vendored GLib string-array iterator fix for [GHSA-wrw7-89jp-8q8g](https://github.com/advisories/GHSA-wrw7-89jp-8q8g); it does not run the upstream GTK test suite. A failed regression prevents publication.

## Publish a version

1. Update the version in `package.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`. Update `Cargo.lock` by running Cargo normally, then verify it with `node scripts/release-info.mjs`.
2. Update `CHANGELOG.md` and the release-note template for the final behavior, complete the checks and merge the release commit.
3. Update `docs/UPDATE-NOTES.md`. These plain-text release notes appear in the app's confirmation dialog. Create and push the matching tag, for example `v0.6.0`. The existing tag can also be selected through the manual release workflow.
4. The workflow checks all version files and the presence of the updater signing key, reruns CI for the tagged commit, then builds all four targets. Every updater package must have its Tauri signature. Only when every build succeeds does its final job receive permission to create a release.

Tags must match the version exactly. A prerelease suffix such as `v0.6.1-rc.1` creates a GitHub prerelease and never changes the stable update channel. Publication is serialized, and an older stable version cannot replace a newer one as GitHub's latest release. Existing releases are never overwritten automatically. If a publication failed after creating its draft, inspect that draft before removing it or creating a new version.

## Downloads

| Target | Downloads |
| --- | --- |
| Windows x64 | NSIS `.exe` installer and MSI |
| macOS Apple Silicon | `.app` ZIP and DMG |
| macOS Intel | `.app` ZIP and DMG |
| Ubuntu 24.04 x64 | AppImage and Debian package |

All names contain the version and architecture. Releases also contain signed updater artifacts, `latest.json`, a source ZIP and `SHA256SUMS`. On Linux run `sha256sum --check SHA256SUMS`; on macOS run `shasum -a 256 --check SHA256SUMS` after downloading the listed assets.

Before packaging, `scripts/third-party-notices.mjs` collects installed JavaScript and locked Rust dependency notices into `public/licenses/DEPENDENCIES.txt`, which is bundled with the app. Releases also attach JSON inventories generated by `pnpm licenses list --json` and `cargo metadata --format-version 1 --locked`; those inventories describe dependencies and do not replace their license texts.

Updater signatures authenticate release payloads using the application's embedded public key. They are separate from operating-system code signing: Windows downloads have no Authenticode signature; macOS bundles are ad-hoc signed and not Apple-notarized. These limitations are included in every release's notes. Do not describe updater signatures as a notarized developer identity.

## Updater signing and manifest

The release workflow requires the repository Actions secret `TAURI_SIGNING_PRIVATE_KEY`, containing the long-lived Tauri private key. Set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` too if the key is password-protected; an absent password secret means an empty password. The matching public key is embedded as `plugins.updater.pubkey` in `src-tauri/tauri.conf.json`. Private keys and passwords must never be committed, included in source archives, printed in logs, or provided to pull-request workflows. Keep an independent protected backup: losing the key prevents updates to installations that trust it. Key rotation needs a separately planned transition.

`bundle.createUpdaterArtifacts` and `plugins.updater.requireSignedVersion` must stay `true`. Tauri CLI 2.12.3 or newer binds the version into each signature during `tauri build`; manual signing needs `--app-version VERSION`. A production updater rejects payloads whose signed version differs from the offered version. Local unsigned development builds can explicitly override `createUpdaterArtifacts` to `false`; do not use that override in release builds.

| Updater target | Payload |
| --- | --- |
| `darwin-aarch64` | Apple Silicon `.app.tar.gz` |
| `darwin-x86_64` | Intel `.app.tar.gz` |
| `linux-x86_64` | AppImage |
| `windows-x86_64-nsis` | NSIS `.exe` |
| `windows-x86_64-msi` | MSI |

The generic `windows-x86_64` entry points to NSIS for compatibility. Installer-aware clients prefer their matching MSI or NSIS entry. Each payload is published together with its `.sig`; signature contents, rather than a signature URL, are included in `latest.json`.

After all platform builds finish, `scripts/updater-manifest.mjs` cryptographically verifies all five distinct updater payloads against the public key embedded in the tagged configuration before creating `latest.json`. Its offline Node verifier uses Ed25519, BLAKE2b-512 for Minisign's current `ED` mode, and the separate global signature over the payload signature and trusted comment, matching the pinned native updater's Minisign checks. Older `Ed` signatures verify the complete payload with a 512 MiB publication limit checked before allocation; larger legacy packages must be re-signed in current streaming `ED` mode. Current `ED` packages are hashed in bounded chunks. Payloads and signatures must be nonempty regular files; signature text is limited to 16 KiB.

Only after both signatures verify is the version field trusted. Publication retains its stricter canonical policy of exactly one version field equal to the checked release version. Modified payloads, exchanged signatures, wrong keys, forged trusted comments and missing/wrong version bindings prevent manifest creation and publication. Generic Windows and NSIS entries share one verified payload; MSI is verified separately. Immutable URLs remain under `releases/download/vVERSION/`, and SHA-256 checksums include the manifest and signatures.

The publication job has no signing secret and adds no package dependency or signing CLI. The native updater still verifies the downloaded package independently before installation. Run `node --test scripts/release-tests.mjs` for temporary in-memory Ed25519 keys, corruption/swap/key/version fixtures, the public upstream Tauri vector and a manifest-generation subprocess with no private-key environment.

The stable endpoint is `https://github.com/ralphschuler/orbitpal/releases/latest/download/latest.json`. To support installed 0.6/0.7 clients after the rename, `latest.json` deliberately uses initial asset URLs under the fixed former `ralphschuler/streamer-ai-cohost` repository path; GitHub redirects them to the same releases. The manifest generator requires the official canonical repository and permits no asset-path override. Keep that redirect intact. See [the migration guide](MIGRATING-TO-ORBITPAL.md). Publication first creates a complete draft, then makes it public and marks a stable release latest. Prereleases remain available for manual downloads. Do not move an existing release tag or replace published assets to repair a version; ship a new version instead.

See [the update guide](UPDATING.md) for user confirmation, restart behavior, and first-install limitations, and the [official Tauri updater documentation](https://v2.tauri.app/plugin/updater/) for the signature format and packaging requirements.

## Workflow boundaries

Release workflows run only for pushed version tags or explicit manual dispatch. They do not run from `pull_request_target` or from untrusted pull-request artifacts. CI and build jobs have read-only repository permissions; only the final publication job has `contents: write`. Checkout tokens are not persisted, third-party actions are pinned to verified commit hashes, and no model or service credentials are provided.

## Product rename compatibility

The display/product name is OrbitPal, while bundle/data/keychain IDs remain stable. The Windows MSI UpgradeCode and NSIS registry identity are pinned to their pre-rename values. The Windows CI job performs a real installer migration smoke with pinned official 0.7.0 payloads on its disposable runner; it never starts the app. See [MIGRATING-TO-ORBITPAL.md](MIGRATING-TO-ORBITPAL.md) before changing product names, Windows templates or updater URLs.
