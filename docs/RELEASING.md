# Releases

Pull requests and changes on `main` run the CI workflow on Linux, Windows, and macOS. Each platform runs `pnpm check`, `pnpm test:run`, the frontend build, packaging-script tests, and `cargo test --locked`. Tests use local fixtures and HTTP mocks; they do not need live model, voice, streaming, or Hindsight accounts.

Linux CI and the Linux release build also run the focused `glib_variant_regression` test with `--release` optimization. It exercises the vendored GLib string-array iterator fix for [GHSA-wrw7-89jp-8q8g](https://github.com/advisories/GHSA-wrw7-89jp-8q8g); it does not run the upstream GTK test suite. A failed regression prevents publication.

## Publish a version

1. Update the version in `package.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`. Update `Cargo.lock` by running Cargo normally, then verify it with `node scripts/release-info.mjs`.
2. Update `CHANGELOG.md` and the release-note template for the final behavior, complete the checks and merge the release commit.
3. Update `docs/UPDATE-NOTES.md`. These plain-text release notes appear in the app's confirmation dialog. Create and push the matching tag, for example `v0.6.0`. The existing tag can also be selected through the manual release workflow.
4. The workflow checks all version files and the presence of the updater signing key, reruns CI for the tagged commit, then builds all four targets. Every updater package must have its Tauri signature. Only when every build succeeds does its final job receive permission to create a release.

Tags must match the version exactly. A prerelease suffix such as `v0.6.1-rc.1` creates a GitHub prerelease and never changes the stable update channel. Publication is serialized, and an older stable version cannot replace a newer one as GitHub's latest release. Existing releases are never overwritten automatically. If a publication failed after creating its draft, inspect that draft before removing it or creating a new version.

## Downloads

| Target | Downloads |
| --- | --- |
| Windows x64 | NSIS `.exe` installer and MSI |
| macOS Apple Silicon | `.app` ZIP and DMG |
| macOS Intel | `.app` ZIP and DMG |
| Ubuntu 24.04 x64 | AppImage and Debian package |

All names contain the version and architecture. Releases also contain signed updater artifacts, `latest.json`, a source ZIP and `SHA256SUMS`. On Linux run `sha256sum --check SHA256SUMS`; on macOS run `shasum -a 256 --check SHA256SUMS` after downloading the listed assets.

Before packaging, `scripts/third-party-notices.mjs` collects installed JavaScript and locked Rust dependency notices into `public/licenses/DEPENDENCIES.txt`, which is bundled with the app. Releases also attach JSON inventories generated by `pnpm licenses list --json` and `cargo metadata --format-version 1 --locked`; those inventories describe dependencies and do not replace their license texts.

Updater signatures authenticate release payloads using the application's embedded public key. They are separate from operating-system code signing. Windows downloads have no Authenticode signature. Public macOS releases through **v0.9.0** are ad-hoc signed; the next release pipeline requires a persistent self-signed certificate and remains **not Apple-notarized**. These limitations must be stated in that release's notes. Do not describe updater signatures or our own certificate as an Apple-verified developer identity.

The macOS bundle verifier pins the existing bundle/signing identifier, product and executable names, packaged version and sealed microphone entitlement. It also requires the actual signer certificate's reviewed SHA-256 and an exact certificate-bound designated requirement. This enables persistent code identity; real macOS privacy acceptance across an update is still a separate manual check. Do not change the bundle ID or reset user privacy grants.

## Persistent self-signed macOS identity

`release/macos-signing-policy.json` selects the free, maintainer-owned self-signed mode for **both architectures**. Its public certificate pin starts unset: release validation fails closed until a maintainer provisions, independently reviews and commits the public certificate/pin. Missing secrets, a different certificate, a changed/expired identity, failed signing or a weaker designated requirement stop the release. There is no ad-hoc fallback.

After independent review, run the offline preparation command with a new, protected absolute directory **outside this checkout**:

```sh
node scripts/provision-macos-identity.mjs /ABSOLUTE/PROTECTED/NEW-DIRECTORY
```

The command creates a ten-year RSA codesigning certificate, an encrypted private key, encrypted `identity.p12`, generated `password.txt`, and public policy. Files are mode `0600`, directory `0700`. It neither imports a key into the Mac, changes trust/TCC, uploads a secret nor signs an app. Never run it again to produce routine releases: those must keep the same identity. Keep independently protected backups of archive/key and password and record custody/expiry. Lost or changed identity may require new OS permission grants.

Review the public SHA-256 out of band, copy **only** `certificate.pem` to `release/macos-signing-certificate.pem` and `public-policy.json` to `release/macos-signing-policy.json`, and review that source change. Upload `MACOS_CODESIGN_P12` as the archive's single-line base64 and `MACOS_CODESIGN_PASSWORD` as the exact password using `gh secret set NAME --repo ralphschuler/orbitpal` with **stdin**, never `--body SECRET` or a secret in shell arguments. A reviewed local Node process can send `readFileSync(archive).toString('base64')` / `readFileSync(passwordFile)` through `spawnSync('gh', ['secret','set',NAME,'--repo','ralphschuler/orbitpal'], {input: value, stdio:['pipe','pipe','pipe']})`, check status and print no command output. Do not paste private values into chats, logs or the repo. CI uses the same two secrets for both macOS targets; they are not present in PR jobs or the publisher.

`macos-release-signing.mjs` runs only on disposable GitHub-hosted macOS runners. It decodes the archive into a private temporary file, creates a temporary keychain and imports only the pinned certificate/key. It never changes system/user Trust Settings, SIP or authorization rules and needs no `sudo`. Password-bearing `security` commands are piped to its interactive stdin; no secret password enters a child process's argv or logs. The exact certificate fingerprint selects the signer. A build-only `codesign` wrapper enforces `identifier "studio.streamer-ai.cohost" and certificate leaf = H"CERTIFICATE_SHA1"` while Tauri signs the app, **before** it creates DMGs and updater archives. The full certificate is additionally pinned using SHA-256. No name-only, identifier-only, binary-hash-only or alternative-key requirement is accepted. [Apple documents](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html) that requirement verification consults Trust Settings only when the requirement explicitly uses `trusted`; our exact certificate-bound requirement does not.

The signer is supplied through `APPLE_SIGNING_IDENTITY`, not `APPLE_CERTIFICATE`: the pinned Tauri CLI 2.12.3 automatic importer enumerates Apple certificate prefixes/team IDs and does not accept our arbitrary self-signed certificate. See its [bundler implementation](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.12.3/crates/tauri-bundler/src/bundle/macos/sign.rs) and [identity selection](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.12.3/crates/tauri-macos-sign/src/keychain/identity.rs). No Apple notarization variables are supplied. The build subprocess receives no archive/password environment variables. Cleanup runs in `finally` and an `always()` workflow step; it removes the temporary keychain/files and restores the runner's search list. Any unconfirmed cleanup fails the job, prevents publication and requires disposal of the hosted runner; force-killed runners are disposed of too. No trust certificate is installed on users' Macs.

CI signs two minimal synthetic Mach-O app versions with one temporary fixture identity, verifies the prior certificate-bound requirement accepts the second, and rejects a second key with the same name and changed signed resources. It never starts those apps or uses production keys. This proves codesigning continuity, **not TCC permission retention**. Before claiming that retention, record a real old→new OrbitPal update with microphone/screen grants on supported macOS versions and both architectures. The transition from ad-hoc v0.9.0 can require one last permission grant. Gatekeeper/manual first-launch approval remains separate; no Apple notarization or zero-prompts guarantee is claimed. See [macOS permissions](MACOS-PERMISSIONS.md).

## Updater signing and manifest

The release workflow requires the repository Actions secret `TAURI_SIGNING_PRIVATE_KEY`, containing the long-lived Tauri private key. Set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` too if the key is password-protected; an absent password secret means an empty password. The matching public key is embedded as `plugins.updater.pubkey` in `src-tauri/tauri.conf.json`. Private keys and passwords must never be committed, included in source archives, printed in logs, or provided to pull-request workflows. Keep an independent protected backup: losing the key prevents updates to installations that trust it. Key rotation needs a separately planned transition.

`bundle.createUpdaterArtifacts` and `plugins.updater.requireSignedVersion` must stay `true`. Tauri CLI 2.12.3 or newer binds the version into each signature during `tauri build`; manual signing needs `--app-version VERSION`. A production updater rejects payloads whose signed version differs from the offered version. Local unsigned development builds can explicitly override `createUpdaterArtifacts` to `false`; do not use that override in release builds.

| Updater target | Payload |
| --- | --- |
| `darwin-aarch64` | Apple Silicon `.app.tar.gz` |
| `darwin-x86_64` | Intel `.app.tar.gz` |
| `linux-x86_64` | AppImage |
| `windows-x86_64-nsis` | NSIS `.exe` |
| `windows-x86_64-msi` | MSI |

The generic `windows-x86_64` entry points to NSIS for compatibility. Installer-aware clients prefer their matching MSI or NSIS entry. Each payload is published together with its `.sig`; signature contents, rather than a signature URL, are included in `latest.json`.

After all platform builds finish, `scripts/updater-manifest.mjs` requires nonempty regular payload and signature files, validates signature format, configured key ID and signed version, and writes immutable URLs under `releases/download/vVERSION/`. These structural checks complement the cryptographic verification performed by the native updater before installation. Missing artifacts or mismatched signatures prevent publication. SHA-256 checksums include the manifest and signatures.

The stable endpoint is `https://github.com/ralphschuler/orbitpal/releases/latest/download/latest.json`. To support installed 0.6/0.7 clients after the rename, `latest.json` deliberately uses initial asset URLs under the fixed former `ralphschuler/streamer-ai-cohost` repository path; GitHub redirects them to the same releases. The manifest generator requires the official canonical repository and permits no asset-path override. Keep that redirect intact. See [the migration guide](MIGRATING-TO-ORBITPAL.md). Publication first creates a complete draft, then makes it public and marks a stable release latest. Prereleases remain available for manual downloads. Do not move an existing release tag or replace published assets to repair a version; ship a new version instead.

See [the update guide](UPDATING.md) for user confirmation, restart behavior, and first-install limitations, and the [official Tauri updater documentation](https://v2.tauri.app/plugin/updater/) for the signature format and packaging requirements.

## Workflow boundaries

Release workflows run only for pushed version tags or explicit manual dispatch. They do not run from `pull_request_target` or from untrusted pull-request artifacts. CI and build jobs have read-only repository permissions; only the final publication job has `contents: write`. Checkout tokens are not persisted, third-party actions are pinned to verified commit hashes, and no model or service credentials are provided.

## Product rename compatibility

The display/product name is OrbitPal, while bundle/data/keychain IDs remain stable. The Windows MSI UpgradeCode and NSIS registry identity are pinned to their pre-rename values. The Windows CI job performs a real installer migration smoke with pinned official 0.7.0 payloads on its disposable runner; it never starts the app. See [MIGRATING-TO-ORBITPAL.md](MIGRATING-TO-ORBITPAL.md) before changing product names, Windows templates or updater URLs.
