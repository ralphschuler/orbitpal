# Local character-life persistence

This implements [#68](https://github.com/ralphschuler/orbitpal/issues/68) on the real SQLite Store, building on [the pure domain contract](LIFE-DOMAIN.md). Life data is separate from profiles, conversation messages, credentials, document files and Hindsight. No Tauri/MCP command or runtime/session activation is added here. The native runtime (#69) owns any future scheduling and explicit session start.

## Storage and ownership

The additive `life_schema` table records storage version **1**. `bot_life_states` has one bot-keyed domain snapshot, its revision, a bounded wall-clock checkpoint and the explicit 64-bit RNG state encoded as 16 hexadecimal characters. `bot_life_events` contains that bot's last **128** structured committed records with matching revisions. The snapshot and event table carry the same validated suffix; neither is accepted when they disagree. Domain schema version and storage version are checked independently.

All Life APIs bind an explicit bot ID to an existing `bot_profiles` row. A scoped Store may access only its fixed bot, regardless of the currently selected Studio bot. Domain ActorId must match the row key, and action IDs also retain their world binding. IDs preserve the existing 1–96-byte ASCII bot-ID grammar, including leading `_` and `-`. Unknown bots are rejected; loading missing life data returns `None`, while corrupted/unavailable life data returns a fixed typed error. It is never silently replaced with fresh needs or an empty history.

`initialize_life` creates a genuinely new lineage once. Reinitializing an existing row is rejected, so copying settings or retrying initialization cannot reset monotonic action identities, completion watermarks or randomness. `load_life` uses a SQLite read transaction to observe the state and its event suffix consistently while other connections commit.

The implementation admits at most 1,024 initialized Life bots, 256 KiB per state and 8 KiB per event. It reads lengths and bounded CASE-selected values before copying JSON, RNG, origin or recovery ID strings into Rust. Oversized documents and extra retained event rows fail closed. JSON validation rejects unknown fields/schema, invalid IDs, non-finite/unbounded values and inconsistent lifecycle data through the actual domain deserializer. Error messages contain fixed categories, never raw SQL failures, payload snippets, paths, bot names, credential values or private content.

## Atomic writes and snapshot cadence

`apply_life_event(bot_id, expected_revision, elapsed_ms, event, now_ms)` obtains an immediate transaction, loads and validates the current row, and checks the expected revision before calling the actual pure reducer. It commits the resulting snapshot, RNG state, checkpoint and new event together, then prunes the matching event suffix inside the same transaction. The actual transaction contents are reread and checked before commit. Insertion errors, commit errors and dropped/uncommitted transactions leave every prior snapshot/event/RNG value intact. Competing Store connections cannot both commit the same expected revision; the loser must reload rather than silently overwrite.

A relevant planned/started/completed/cancelled or explicit needs transition can persist immediately. A Tick-only checkpoint is deferred until its **accumulated simulation elapsed time reaches 30 seconds**. Deferred ticks return the unchanged confirmed snapshot and no intent. The caller must measure elapsed time since the last confirmed snapshot, not merely the last render frame or deferred attempt. Once accepted, one tick still advances at most the domain's 60-second bound and emits one clock record. Render frames do not have a persistence callback. The future runtime must use its own controlled monotonic clock and slow scheduling; arbitrary viewer/model input must never supply these arguments.

Duplicate and stale acknowledgements preserve their domain no-op behavior and perform no state/event write. A replay with an obsolete expected revision fails the compare-and-swap check. Completion credit remains native, exactly once and fixed at planning; no persistence method accepts replacement rewards as part of Complete.

## Restart, absence and optional availability

Opening the main Store inspects life metadata and recovers each valid bot in its own atomic transaction. Scoped Store construction shares that recovery status and does **not** repeat restart handling. For an interrupted Planned/Started action, recovery records `Cancelled` with `CancelReason::Restart` and gives no completion reward. Its actor/action watermarks remain intact. A restored terminal action stays informational. None of these records represents a running action, reservation, session or grant.

Offline passage is computed from the caller-supplied current wall time and last saved checkpoint with saturating subtraction and a maximum of **60 seconds**. It changes only the bounded simulation clock. It does not decay needs, remove progress, invent goals or replay actions, model requests, animations or audio. A backwards wall-clock jump advances nothing and rebases the checkpoint. Reopening again at the same checkpoint does nothing; there is no accumulated absence debt or catch-up chain.

Stored event origins explicitly distinguish `live`, `restart` and `offline`. Offline records may only contain clock advancement; restart records may only contain restart cancellation. Invalid combinations are rejected. A later recap must not describe offline clock progression as an experienced activity. Live data still needs the domain's confirmed completion; dispatch or planning alone is not success. The normal mutation API cannot manufacture `Restart` cancellation records.

Optional Life corruption does not make OrbitPal's profiles, chat or general settings unusable. A bad bot's payload remains untouched and its Life APIs report unavailable; other valid bots recover independently. Unsupported or partially initialized global life schema disables Life operations while ordinary Store access remains available. `life_availability(bot_id)` exposes `Ready`, `NotInitialized`, or `Unavailable(fixed_reason)` for the future runtime/settings views (#69/#78). No unavailable state authorizes a session. Malformed/non-text, invalid UTF-8 or overlong owner rows are quarantined without blocking valid bots; `life_recovery_report()` supplies bounded warning counts and fixed schema categories without payloads or other bot IDs. Startup errors are retained by the scoped Store views; repair/retry UX is future product work. After an intentional external repair, restart the app to rerun validated recovery.

## Migration and portable profile boundaries

The supported historical migration is the actual pre-Life database: existing settings/messages/bot/profile/extension tables with **no** life tables. All three v1 tables and their version marker are created in one transaction. An interrupted migration rolls back to that genuine old layout and can be retried. There is no invented v0 prototype format. A version marker without its expected tables, unversioned partial life tables, future versions or damaged rows are not guessed, deleted or overwritten. Schema creation failure is exposed through optional-Life availability and leaves the migration transaction rolled back.

Life tables are absent from the existing profile export format, which remains version 2. New/copied/imported bots receive their own existing bot identity and no life row or lifecycle authority. Import collision checks include orphaned local state/event identities as well as registered profiles and directories; a package cannot claim an orphan's old local lineage. An uninspectable optional life layout conservatively causes allocation of a new import ID. Reserved top-level payload keys `lifeState`, `lifeEvents`, `lifeSnapshot`, `lifeSessions` are stripped at save/copy/import/export boundaries; configuration and unrelated profile fields keep their existing behavior. A package's unrecognized root life payload is not imported into SQLite. Any future explicit life export needs a separate ownership, privacy and lineage contract.

The existing screen-grant reset, credential-reference isolation, disabled imported tools/Skill scripts and output defaults remain in force. Nothing in life data turns on microphone, screen capture, model access, MCP, Skills or a native autonomy session. Saving life state does not add artificial conversation messages or transfer one bot's memories to another.

## Validation and limits

Actual Store tests create temporary directories and SQLite databases, never a developer profile/database. They use controlled wall/simulation time and the actual reducer. Fixtures cover the real old schema, v1 reopen, interruption/cancellation, retention and idempotency after eviction, two independent bots and scoped Stores, two-connection revision races, failed inserts and deferred commits, interrupted transactions/migrations, malformed/future/oversized data, optional availability with one corrupt and one valid bot, clock jumps, checkpoint cadence, and real existing copy/import/export paths. No live credential store, microphone, screenshot, stream account, Hindsight or paid provider is contacted.

Run the focused native suite with `cargo test --manifest-path src-tauri/Cargo.toml --locked --lib storage::life_store::tests`; complete repository checks still apply before integration. These tests establish native storage behavior. They do not demonstrate native LifeRuntime scheduling, hidden-window activity, rendered self-care, social scenes or a UI repair flow. Those remain their separate issues. Substantial AI assistance was used in implementation and test preparation.
